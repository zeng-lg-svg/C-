# LLFCChat 多业务线程与会话清理改造

日期：2026-11-12。目标：改善单业务线程遇到阻塞操作时对其他连接的影响，学习按会话串行调度和会话清理的边界。本改造由 AI 辅助编写与验证，需要结合源码进一步复盘；新构建尚未作为原服务启动。

## 一、背景与原问题

原版 `LogicSystem` 只有一个业务工作线程。此前隔离实验中，A 登录时同步等待被占用的 Redis 锁，B 的心跳业务响应约 4.72 秒后才返回；这是单次功能实验，不是性能压测。此前还发现业务回调在队列锁内执行，会阻挡网络线程入队；已有工作区改动将回调移到锁外，但仍只有一个业务工作线程。

## 二、这次代码改了什么

两份节点分别修改 `server/ChatServer/` 与 `server/ChatServer2/` 中相同职责的文件；下文用 ChatServer2 举例。

1. `ShardedExecutor.h`：由独立学习实验发展而来，包含多个分片；每个分片拥有任务队列、互斥锁、条件变量及一个工作线程。任务依据 `std::hash<std::string>{}(session_id) % 分片数` 分配，队列在锁内入队、取出，任务在锁外执行。相同连接的任务进入同一队列，不同连接可能并行，也可能哈希到同一队列。
2. `LogicSystem.h/.cpp`：`_executor(2)` 当前固定创建两个分片，先注册回调，再根据会话 ID 投递消息。`ProcessMessage()` 在连接已关闭时不再执行业务；`PostSessionCleanup()` 把断开清理投递到同一分片。这里保证的是任务实际入队后的该分片处理顺序，不是跨连接或跨服务器的全局顺序。
3. `CSession.h/.cpp`：`Close()` 在互斥锁保护下标记连接关闭并关闭 socket，重复调用不再重复关闭；`IsClosed()` 在相同锁下读取状态。`DealExceptionSession()` 利用 `_cleanup_queued.exchange(true)` 去重，将实际清理提交到业务分片；若提交失败，当前实现等待执行器停止后同步尝试清理。`PerformCleanup()` 才读取用户 ID、根据 Redis 中的 session ID 判断是否属于当前会话并处理本地映射及在线记录。
4. `LoginHandler()`：获取锁后检查会话是否已经关闭，关闭则不继续绑定在线状态。若恰好在检查后断开，登录写入和断开清理仍可能交错；同会话分片保证已成功入队的清理会在先前的登录任务完成后执行，不保证任意时刻 Redis 没有短暂过期状态。
5. `ChatServer.cpp`：在停止网络线程、关闭 gRPC 并结束计时器后，显式调用 `LogicSystem::Stop()`，等待已接收任务排空，再从 main 返回并执行已有 Redis 清理。停止后拒绝新任务；该设计的安全性仍依赖所有任务生产者确实已退出，异常启动和所有退出路径未完全验证。
6. 前一阶段 `CSession::_user_uid` 已改为 `std::atomic<int>` 并使用 load/store，解决该变量并发读写的数据竞争；它不保证跨字段的一致性和业务顺序。

## 三、关键时序

正常情况：网络线程接收完整消息 -> 用 session_id 投递到对应分片 -> 工作线程取出消息并释放队列锁 -> 执行业务处理。

连接断开：网络侧 Close() -> DealExceptionSession() 去重投递清理 -> 相同分片中排在前面的任务结束 -> PerformCleanup() 检查 Redis 的 session ID 再清理。重复清理事件不会重复入队。跨节点或同账户不同连接有不同 session_id，不能仅依靠分片串行化；仍依赖 Redis 锁等协调，而锁过期、获取失败和 Redis 多键一致性未完全解决。

停止：网络及 gRPC 生产者停止 -> 分片执行器拒绝新任务、唤醒工作线程、处理已接收任务并 join -> 现有 Redis 清理。耗时或卡住的任务可能使 shutdown 长时间等待；目前没有强制任务超时、取消或队列容量限制。

- 独立 ChatServer2 + 临时 Redis + 临时 MySQL + 模拟 TCP 客户端：同节点登录、文本消息、相同客户端 ID 重试并避免重复通知；A 等用户锁时，确认 B 属于另一个分片，其心跳在单次实验中约 0.00 秒响应。该数字仅为一次功能实验，不能作性能指标。
- 同一隔离环境：登录等待锁期间客户端断开，最终未留下在线记录；新程序执行 SIGTERM 正常退出。
- 两节点各自独立测试：同账号先后登录、旧连接收到下线通知并断开、新连接 Redis 状态保留和心跳正常；SIGTERM 正常退出。

- 以上临时测试数据库、Redis 和服务已清理。此前学习实验使用自造任务测试了同分片顺序、不同分片并行及停止后拒绝任务。

## 五、未验证与注意事项

- 未对真实 Qt 客户端做回归，未上线、未进行压力/稳定性测试或 ThreadSanitizer 全量并发检测，不能宣称并发能力或稳定性达到任何指标。
- 未穷举多入口同时断开、重复登录竞争、Redis 锁失效/锁租期过期、Redis 写入部分失败、节点宕机、任务回调长时间阻塞、停止时生产者仍提交、队列投递失败的所有时序。
- 普通任务每个分片最多等待 1024 个，过载会关闭连接；清理任务绕过普通容量限制，因此总体队列仍可能增长。连接池容量、同步 Redis/gRPC 调用、热点会话碰撞和 2 个固定分片仍可能成为瓶颈。动态变更分片数需要重新设计顺序和迁移，不能直接热改。
- `Close()` 与 socket 异步操作跨线程的完整线程安全性尚需检查；当前代码不能据此声称全部数据竞争已消除。Redis 分布式锁过期后旧持有者继续操作的问题也未解决。
- 对已关闭连接跳过尚未执行的业务任务是一项行为变化；客户端需要处理超时/断线。清理任务投递失败时的同步兜底可能等待其他慢任务；Redis 清理失败只记录日志、不自动重试，是否需要超时、隔离执行器和严格的停机协议待进一步设计。
- MySQL 幂等依赖 `client_msg_id` 字段和联合唯一索引；已存在环境尚须确认迁移，Git 记录不能自动迁移数据库。去重不等于可靠投递。
- 切换真实进程前，应先审核差异、确认生产者和 Redis/MySQL 的停止顺序、补充故障与负载测试并确认配置；不要将已验证的临时环境误认为原运行实例已经更新。

## 六、面试复盘

建议按“问题 -> 原因 -> 方案 -> 验证 -> 限制”讲：单个逻辑线程和锁内执行回调可能造成队头阻塞；先缩短队列锁，再按 session 固定分片，由各分片单线程顺序处理；断开清理投递到同一分片，并在服务停止时等待任务完成；通过隔离同节点与跨节点功能实验检查消息、断开和重登；未完成压测、所有异常时序和可靠投递。注明基于 LLFCChat 开源项目并在 AI 辅助下实现与验证，自己能够解释细节后再写入简历。


## 七、补充完善：队列容量与 Redis 在线状态原子操作

### 7.1 普通任务限流与清理

- `ShardedExecutor` 默认每个分片最多排队 1024 个普通任务，不计当前正在执行的任务；达到上限时 `post()` 返回 false。当前 `PostMsgToQue()` 对拒绝采用关闭连接的策略，未实现返回“服务繁忙”协议或客户端自动重试。
- `postCritical()` 将清理任务放到同一个 FIFO 队列，但绕过普通任务容量限制；保证其位置在已接收任务之后，不代表清理获得优先级。退出状态仍会拒绝投递，此时现有逻辑先等待执行器停止再同步尝试清理。每个会话通过 `_cleanup_queued` 避免重复投递。
- 清理任务可以绕过上限，因此不是全局有界队列；大量不同连接同时断开仍可能导致积压。阻塞任务可能让清理和 shutdown 长时间等待，需要后续进行容量、超时和停机设计。
- `learning_sharded/queue_capacity_test.cpp` 可重复验证单分片上限、拒绝普通任务、清理按序进入、排空及停止后拒绝。独立服务单次过载实验：人为阻塞 A 的分片并向同分片的 B 发送多条心跳，B 连接被关闭，处理完成后 B 的在线记录被清理；不是压测或所有时序的证明。

### 7.2 在线记录写入与条件删除

- `RedisMgr::PublishOnlineSession()` 使用一条 `MSET` 写入 `uip_<uid>` 和 `usession_<uid>`。失败时登录响应 `LOGIN_ONLINE_STATE_FAILED` (1103)，尝试按会话 ID 清理可能已经写入的状态，并不设置本地已登录用户 ID。Redis 连接中断时命令结果仍可能不确定，补偿操作也可能失败。
- `RedisMgr::ClearOnlineSessionIfMatch()` 使用 Lua 脚本，在 Redis 内一次性比较当前 session ID、匹配时删除 session 和节点两个键；旧会话清理时如果记录已属于新会话，不删除新状态。`PerformCleanup()` 使用此方法，操作失败时记录可能残留状态的日志，并清理本地会话；目前没有持久化重试，Redis 故障时不能保证最终清理。
- 原子写入与条件删除可以消除新版本之间的两键部分更新及比较/删除间隙，但不能防止已过期的锁持有者随后发布旧状态；也未解决进程崩溃、Redis 不可用或跨节点所有时序。同一份用户在线状态不能在不同 Redis Cluster hash slot 使用该两键 Lua 脚本；当前方案基于单 Redis 实例。新旧节点混跑时，旧节点仍可能分步写两键，需在部署设计中考虑，不可宣称无风险滚动升级。
